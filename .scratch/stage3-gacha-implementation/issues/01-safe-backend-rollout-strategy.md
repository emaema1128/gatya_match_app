## Question

bloomにはステージング環境が存在しない(`bloom_api_client.dart`のコメント参照)。ガチャ機能のために新設する4つのバックエンド変更——①新しい`PayCost`コストタイプ(ガチャ1回分)、②「見た相手+いつ見たか」を記録する新規テーブル、③`registUser`への初期ポイント自動付与、④候補枯渇時のサービスポイント付与ロジック——を、本番データベース・本番コードに対してどう安全に投入するかを決定する。

含めるべき論点:

1. スキーマ変更(新規テーブル追加)を、既存データやロジックを壊さずに行う方法(追加のみ・削除や既存列変更は避ける、など)。
2. 新しいロジック(`route_api.php`への新規`execute_function`追加など)を、ユーザーがまだ使わない状態で先に本番へデプロイし、動作確認してから有効化する方法があるか(機能フラグ、テスト用アカウントでの限定確認等)。
3. ローカルでの動作確認手段があるか(ローカルPHP実行環境+本番DBのコピー、等)、それとも本番に対して直接確認するしかないか。
4. 万が一問題が起きた時のロールバック方針(新規テーブル・新規カラムは追加のみなので削除すれば実質的に無害化できるはずだが、実際に確認する)。

決定+実装(このマップの方針)。

## Answer

[02-spin-endpoint-design](02-spin-endpoint-design.md)の結果、実際の変更範囲が「新しいPHP定数1つ+新しい`execute_function`ケース1つ」という**追加のみ**の変更に収まったため、当初懸念していたリスクは大幅に下がった。

**訂正(実装時にさらにリスクが下がった)**: 当初は「見た記録」用に新規テーブル`gacha_seen`を作る想定だったが、検討の結果、既存の`point_log`テーブル(ポイント消費の副作用として自動的に記録される)を流用する設計に変更した([02](02-spin-endpoint-design.md)参照)。これにより**スキーマ変更(新規テーブル作成すら)が一切不要**になった。

1. **スキーマ変更**: なし。既存テーブル(`user`/`likes`/`matches`/`point_log`等)への列追加・変更・新規テーブル作成は一切ない。

2. **新エンドポイントは「使われるまで無害」**: `spinGacha`という新しい`execute_function`ケースは、Flutterクライアント(チケット05)が呼び始めるまで誰にも影響しない。機能フラグを別途用意する必要はなく、「バックエンドを先にデプロイ→動作確認→クライアントを繋ぐ」という順序自体が安全装置になる。

3. **検証方法**: 開発者自身のテスト用アカウント(既存)を使い、本番に対して直接動作確認する。Stage1/2/4で既に確立されている「有効なテストアカウントで実機確認」という方針と一貫させる。ポイント増減は、そのテストアカウント自身のデータにしか影響しない。

4. **ロールバック**: 追加のみの変更(かつスキーマ変更ゼロ)のため、問題が起きてもPHPコード(`route_api.php`の2箇所+`Class_PayCost.php`の定数1つ+新規`Class_GachaApi.php`)を戻すだけで無害化できる。

5. **実施順序**: ①`PayCost::GACHA_SPIN`定数+`spinGacha`エンドポイントのPHPコードをデプロイ(この時点では誰も呼ばないので無害) → ②テストアカウントで動作確認 → ③チケット05(Flutterクライアント)を実装してつなぐ。
